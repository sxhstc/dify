# OneSpec BugFix — Bug 分析与修复计划

从禅道拉取 **缺陷（Bug）工作项**，结合代码库分析根因与影响范围，生成 **`bugfix.md`**（含修复任务、回归要点）。产物结构类似轻量版 `tasks.md`，但**不走** `changes/proposal/design` 全流程。

**禅道 MCP**：服务器名一般为 **`user-zentao`**（以 Settings → MCP 为准）。

<background_information>
- **定位**：介于「自然语言让 AI 改代码」与「OneSpec 完整变更闭环」之间的 **轻量 Bug 修复流程**。
- **适用场景**：明确的缺陷修复，不涉及大量新功能开发、数据模型变更或跨模块架构调整。
- **不适用**：若 Bug 修复实质是「做一个新功能」或涉及 ≥3 个模块的大改，应走 `/onespec-change` 完整流程。
- **成功标准**：
  - `bugfix.md` 含真实的禅道 Bug 字段（不编造）
  - 根因分析基于实际代码（不臆测）
  - 修复任务可执行、可验收
  - 禅道 Bug 状态更新为「处理中」
</background_information>

<instructions>
## 参数
- `bugId`:（必填）禅道 **Bug ID**（Bug 详情页的 ID）。

## 执行步骤

### 1. 获取 Bug 详情

1. 调用 **`get_bugs_bugID`**：`bugID` = `<bugId>`。
2. **校验**：检查返回是否为有效 Bug（返回数据包含 `id`、`title` 等字段）。
   - 若返回无效或为空 → 终止：「Bug ID 无效或不存在，请确认 ID。」
3. **解析字段**（以 API 返回为准，无则标 **—**）：
   - `id`（Bug ID）、`title`（标题）
   - `status`（状态）、`severity`（严重程度）、`pri`（优先级）
   - `openedBy`（创建人）、`assignedTo`（指派给）
   - `openedDate`（创建时间）
   - `execution`（所属执行/迭代）

### 2. 更新禅道 Bug 状态（可选）

1. 尝试通过 **`put_bugs_bugID`** 更新 Bug 的 `assignedTo` 或其他可编辑字段以标记正在处理。
2. 若禅道不支持直接设置「处理中」状态或更新失败 → 记录警告，跳过此步骤，不中断流程。

### 3. 代码根因分析

1. **关键词提取**：从 Bug 标题 + 描述中提取关键词（模块名、页面名、接口名、字段名等）。
2. **代码搜索**：
   - 在代码库中搜索关键词，定位相关文件（前端组件、后端 Controller/Service、配置等）。
   - 读取相关文件，理解现有逻辑。
3. **根因推断**：
   - 结合 Bug 描述的「预期 vs 实际」，分析代码中的问题所在。
   - 确定是逻辑错误、数据处理、样式/布局、配置、还是接口问题。
   - **如无法确定根因** → 在 `bugfix.md` 中标注「根因待确认」，列出可疑文件供人工排查。
4. **影响范围评估**：
   - 列出受影响的模块、接口、数据、用户面。

### 4. 生成修复任务

1. **拆解修复点**：
   - 每个独立的代码修改点拆为一条任务（Bug 修复通常 1~3 条）。
   - 每条任务含：标题、修改的文件路径、具体修改内容、验收标准、预计工时。
   - **粒度判断**：若修复任务超过 5 条或预计总工时超过 16 小时，**提醒用户**考虑走 `/onespec-change` 完整流程。
2. **回归测试要点**：
   - 列出原始缺陷的复现路径（修复后应不再复现）。
   - 列出可能受影响的相关功能（防止回归）。
   - 列出需注意的边界条件。

### 5. 写入 bugfix.md

1. **目录名** `<slug>` 规则：
   - 以 `bug-<bugId>` + Bug 标题的安全化 slug 拼接，如 Bug ID `123`、标题「后管页面排版调整」→ `bug-123-admin-layout-fix`。
   - 非法字符替换为 `-`，合并连续 `-`，长度上限 60 字符。
2. **读取模板**：`.cursor/commands/spec-templates/bugfix.md`。
3. **写入**：`onespec/bugs/<slug>/bugfix.md`。
4. **填充规则**：
   - Frontmatter 中的 `status` 设为 `pending`（待实现）。
   - 第一节「缺陷描述」：**原文保留** API 返回的描述（HTML 转 Markdown 或纯文本）。
   - 第二~三节「根因分析 / 影响范围」：基于步骤 3 的代码分析填写。
   - 第四节「修复任务」：基于步骤 4 的拆解填写，复选框格式（同 tasks.md）。
   - 第五节「回归测试要点」：基于步骤 4 的回归分析填写。
   - 第六节「SQL / 配置变更」：若无则留空。
   - 第七节「关联文档」：填写实际路径。

### 6. 提示用户

1. 输出摘要：
   - Bug ID 与标题
   - 根因简述（一句话）
   - 修复任务数 + 预计总工时
   - 禅道状态是否已更新
2. 后续指引：
   - 「请审查 `bugfix.md` 的根因分析与修复任务。确认后运行 `/onespec-bugfix-implement <slug>` 开始修复。」
   - 若任务过多：「修复任务较多（N 条，约 X 小时），建议考虑走 `/onespec-change` 完整流程。」

## 关键约束

- **禁止在 bugfix 阶段改代码**：本命令**仅**产出 `bugfix.md`（及本流程允许的禅道 Bug 状态更新）；**不得**修改业务源码、SQL、部署/应用配置等。实际动手修复须由 **`/onespec-bugfix-implement`** 执行。
- **不编造**：Bug 字段来自 `get_bugs_bugID`，根因来自实际代码分析；不确定的标注「待确认」。
- **轻量定位**：不生成 proposal / design / Delta Spec；`bugfix.md` 是自包含的单文件。
- **路径基准**：命令中的文件读写路径以本命令文件所在仓库的根目录为基准，不限制跨工作区的上下文收集。
</instructions>

## 工具指导
- **先读取**：加载 Bug 详情 + 相关代码后再写 `bugfix.md`
- **最后写入**：分析完成后一次性写入 `bugfix.md`，避免半成品；**勿**在本阶段修改业务代码（见上文关键约束）。

## 安全与回退

### 错误场景
- **Bug ID 不存在**：终止，提示确认 ID
- **非 Bug 类型**：警告但继续（用户确认后）
- **代码搜索无结果**：根因标注「待确认」，列出搜索关键词供人工排查
- **禅道状态更新失败**：记录警告，不阻断 bugfix.md 生成

### 与现有命令的关系
| 场景 | 推荐命令 |
| --- | --- |
| 明确 Bug，修复点 ≤ 5 | **`/onespec-bugfix`** → **`/onespec-bugfix-implement`** |
| Bug 实质是新功能 / 跨模块大改 | **`/onespec-change`** → design → task → implement |
| 仅需提测清单，不做分析 | **`/onespec-bug-checklist`** |
| Bug 已修复，需要出提测材料 | **`/onespec-bug-checklist`** |
