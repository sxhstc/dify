# OneSpec Task Breakdown

此命令基于 `design.md` 生成 `tasks.md`，并通过 **禅道 MCP** 创建 **Task**（含去重与回填 **禅道任务 ID**）。

**前置（步骤 3 同步）**：**`executionID`**（禅道执行/迭代 **数字 ID**）**必填**（简写或 `--execution`）。**负责人**：未传 **`--assign`** 则 **`post_tasks` 不传 `assignedTo`**，由禅道按 **token 绑定用户**处理；传了 **`--assign`** 则用传入值；**不用** `mcp.json` 的 `username` 兜底。服务器名为 **`user-zentao`**。

> **为何必须显式传执行**：禅道里「版本 / release」对应的是 **执行（Execution）** 实体，可能有多个并行迭代。**不能**在未确认时从 `get_executions` 结果里「随便选一条」——多执行时必须由用户指定，否则会建错迭代。

<background_information>
- **任务**: 将设计 (HOW) 转化为可执行的任务列表 (Plan)，并与禅道任务一致
- **成功标准**:
  - 任务粒度合理（单任务不超过 8 小时）
  - 每个任务均可追溯到设计章节与需求 ID
  - 依赖与并行关系清晰
  - 禅道侧 Task 已创建或去重跳过，且 `tasks.md` 已回填 `禅道任务ID`
</background_information>

## 参数

### 主参数（二选一）

1. **简写（推荐）**：`<storyId>-<executionId>` — **两段均为纯数字**，中间一条连字符，例如 **`9-4`**。  
   - **语义**：`storyId` = 禅道研发需求 / 与 `onespec/changes` 目录前缀一致的 **变更数字 id**；`executionId` = 禅道 **执行（迭代）数字 ID**（与「需求已关联到版本」后页面如 `execution-storyView-9-4.html` 对齐）。  
   - **目录补全**：用 `storyId` 在 `onespec/changes/` 下匹配 **`{storyId}-*/`**；**仅一个目录**则 `name` 取该目录后缀；**多个目录**须请用户改用完整形式 **`{storyId}-{name}`** 并显式指定，**禁止**用 `executionId` 猜 `name`。  
   - **校验（推荐）**：用 MCP **`get_stories_storyID(storyId)`**、**`get_executions_executionID(executionId)`** 各拉一次，与本地 `proposal` 标题/执行名核对，避免 URL 版本差异导致两段数字含义颠倒。  
2. **完整变更目录**：`<id>-<name>` — 第二段 **含字母**（kebab-case），例如 **`9-bank-account-list`**。此时 **`executionID` 必须由 `--execution=`**、简写 **`storyId-executionId` 另一参数** 或 **执行-需求 URL** 提供，规则见下节。

### 标志参数

- `--execution=<executionID>`：禅道执行/迭代 **数字 ID**。与简写同时出现时 **以 `--execution` 为准**（覆盖简写中的执行段）。**与 release 名的关系**：业务名对应执行对象的 `name`/`code`；MCP 建任务要数字 ID；若只给版本名，用 `get_executions` 对 `name`/`code` **唯一匹配**，0 或多条则必须用户明确 ID。  
- `--assign=<account>`：**可选**。禅道任务字段 **`assignedTo` = 指派给谁做**（执行人），**不是**「谁拆解的任务」——拆解是本地 `tasks.md` + Agent/人工，禅道不关心。**何时需要**：给**其他人**领任务、代建任务、或必须写死指派时；**你本人用 token 自己做**时一律**省略**即可，不冗余也不必填。  
- `--sequential`：强制顺序规划，不标记 ` (P)`。  
- `--no-design`：跳过 `design.md`，仅用 `proposal.md` + `specs/`。

### MCP / Token 与负责人（`assignedTo` 规则）

1. **未传 `--assign`**：已配置 **token** 时，**`post_tasks` 不传 `assignedTo`**；由 **禅道按 token 绑定的用户** 处理（创建者/默认指派以禅道为准）。**不使用** `mcp.json` 的 `username` 等字段做兜底。  
2. **传了 `--assign=账号`**：在 `payload` 中写入 **`assignedTo`**，与 token 用户无关，以传入账号为准。

### 执行 ID 解析规则（步骤 3 同步前强制执行）

0. **若主参数匹配** `^\d+-\d+$`（简写）：拆出 `storyId`、`executionId`；`executionID = executionId`；`id = storyId` 用于目录匹配；**不再**因「`get_executions` 仅一条」自动覆盖该执行 ID。  
1. **若用户已提供 `--execution=<id>`**：使用该 `executionID`（若与简写并存，以本项为准）。  
2. **若仍未有 `executionID`**：调用 **`get_executions`** 拉取候选：
   - **仅 1 条**：可在对话中列出该条的 `id`、`name`、`projectName` 后采用，并**提示**「本次因仅有一条执行已自动选用；多迭代并行时请务必传 `--execution`」。
   - **0 条**：不得同步；仅生成本地 `tasks.md`，并提示创建/选择迭代后再传 `--execution`。
   - **≥2 条**：**不得**自动选用；仅生成本地 `tasks.md`（或暂停），输出表格（`id` / `name` / `code` / `status` / `projectName`）请用户回复选用哪条或重新带 `--execution` 执行命令。
3. **若用户提供禅道「执行下的需求」页面链接**（与「把需求关联到版本/迭代」后的视图一致，例如 `.../execution-storyView-9-4.html`）：
   - 链接中通常包含 **两个数字 ID**，分别对应 **研发需求（Story）** 与 **执行（Execution / 迭代）**；**不同禅道版本 URL 参数顺序可能不同**，不得死记「第几个一定是执行」。
   - **推荐解析方式**：将两个候选 ID 分别调用 **`get_stories_storyID`** / **`get_executions_executionID`**（或对照 `get_executions` 列表）做 **一次校验**——与 Story 标题、执行名称（如 `release_v2.5.8`）及本次变更 `proposal` 中的禅道 Story 一致后，再确定 **`executionID` 用于 `post_tasks`**。
   - **拆解逻辑对齐**：`tasks.md` 的拆解仍以本地 `design.md` / `proposal` 为准；禅道侧 **Task 必须建在该 Story 已关联的同一 `executionID` 下**，这样任务、需求、迭代在看板与统计里一致。用户粘贴此类链接时，**视为强烈提示**应采用的执行上下文，优先于「未传 `--execution` 时盲猜 `get_executions` 第一条」。

## 执行步骤
### 1. 准备工作与校验
1.  **上下文识别与参数补全**:
    - **自动推断**:
        - 检查当前活跃的编辑器文件路径，是否包含 `onespec/changes/<id>-<name>/` 模式。
        - 检查最近的对话历史或工具调用，是否刚执行过 `onespec-design`。
    - **参数确认**:
        - 若用户主参数匹配 **`^\d+-\d+$`（简写 `storyId-executionId`）**：拆出 `id` = 首段、`executionID` = 末段；在 `onespec/changes/` 下查找 **`{id}-*/`** 唯一目录以补全 `name`；多目录则终止并提示使用 **`{id}-{name}`** 或简写加明确目录。
        - 如果用户提供了完整 **`id` 和 `name`**（`{id}-{name}` 且第二段非纯数字），直接使用；`executionID` 来自 `--execution`、同轮对话中的执行-需求 URL、或上一条简写规则。
        - 如果用户仅提供了 `id`（单独数字）且无 `executionID`，尝试在 `onespec/changes/` 下查找匹配该 ID 的目录，自动补全 `name`；**执行 ID** 走「执行 ID 解析规则」后续步骤。
        - 如果用户未提供参数，且通过上下文推断出唯一的 `<id>-<name>`，则自动使用。
        - 如果推断出多个可能性，列出选项请用户确认。
        - 如果无法推断，提示用户输入必需参数。
2.  **校验输入文档（兜底策略）**:
    - 检查路径 `onespec/changes/<id>-<name>/design.md` 是否存在：
        - **存在**: 使用 `design.md` 作为主要任务拆解依据（**完整模式**）。
        - **不存在，且用户使用了 `--no-design` 参数或当前为简单变更**: 检查 `proposal.md` 和 `specs/*.md` 是否存在。
            - 若 `proposal.md` 存在：以 `proposal.md` + `specs/` 为输入，进入**轻量模式**拆解任务。
            - 轻量模式下，`tasks.md` 开头需注明"⚠️ 基于 Proposal 直接拆解（无详细设计），任务粒度可能较粗，建议人工复核"。
            - 若 `proposal.md` 也不存在：终止流程，提示用户先运行 `onespec-change`。
        - **不存在，且未使用 `--no-design` 参数**: 终止流程，提示用户: "未找到详细设计文档。如需跳过设计阶段，请使用 `--no-design` 参数，或先运行 `onespec-design` 生成 design.md。"
3.  **读取模板**:
    - 读取任务模板: `.cursor/commands/spec-templates/task.md`。
4.  **确认输出目录**:
    - 目标文件将保存在 `onespec/changes/<id>-<name>/tasks.md`。

### 2. 拆解任务并生成 tasks.md

#### 2.1 任务拆分原则

1.  **契约先行与衔接原则** (关键原则):
    - **接口契约显式化**: 对于涉及前后端交互或跨模块调用的功能，**必须**在编码任务之前，拆解出一个独立的或前置的“接口定义/契约确认”任务。确保在写代码前，双方对入参、出参、错误码达成一致。
    - **联调任务实体化**: 不要将“联调”隐含在功能开发中。对于复杂的业务流程（涉及2个以上模块/角色），**必须**拆解出独立的“集成联调”任务，为联调预留专门的时间。

2.  **模块化组织原则**:
    - **按功能模块分组**: 根据 `design.md` 的实际内容，使用 `##` 二级标题将任务进行逻辑分组。推荐的分组顺序如下（强化首尾衔接）:
      - **契约与模型定义**: API 接口定义、数据库模型变更确认、公共常量/枚举定义。
      - **核心业务功能**（按业务模块细分）
      - **配置管理功能**
      - **性能优化与安全**
      - **集成联调与验收**: 全链路数据流验证、异常流程联调、性能验证。
      - **文档与发布**
    - **优先识别基础/公共能力**: 首先从 `design.md` 中识别并提取基础能力、公共组件或复用模块，优先为这些能力创建任务。

3.  **按功能拆分，不区分前后端**:
    - 剩余业务功能应**按功能特性进行拆分**（而非按前后端分离拆任务）。
    - 确保每个任务都是一个完整的、可独立验收的功能点，可自测、可交付给QA验收的最小价值单元。

4.  **信息完整性原则** - 每个任务必须包含:
    - **预计工时**: `预计工时：X小时` （必须）
    - **详细变更说明**: 必须按以下分类详细说明修改点，明确涉及的文件路径和修改内容：
      - **接口/协议变更**: 新增/修改的 API 路径、消息格式或契约定义。
      - **配置变更**: 涉及的配置文件路径及修改说明（如 Nacos 配置、YAML 属性等）。
      - **后端代码变更**: 涉及的后端逻辑文件路径（如 Controller, Service, Mapper 等）及核心修改逻辑。
      - **前端代码变更**: 涉及的前端组件/页面文件路径（如 Vue, React, JS/TS 等）及核心修改逻辑。
      - **SQL执行**: 涉及的 SQL 脚本路径、表结构变更或数据处理说明。
      *(注：若某类变更不涉及，可省略该分类)*
    - **测试覆盖率要求**: 核心功能 ≥80%，一般功能 ≥70%
    - **设计章节引用**: `参考：design.md § X.X.X` （精确到小节编号）
    - **验收标准**: 功能点、性能指标等（如适用）

5.  **可追溯性原则**:
    - **需求追溯**: 每个任务必须包含 `需求：{{REQUIREMENT_IDS}}` 行（仅填写 ID），且该行必须**紧随任务标题之后**作为第一条子项。
    - **禅道 ID 回填**: 同步后在 `需求：` 行之后添加 `禅道任务ID：{{TASK_ID}}` 行。
    - **内容关联**: 精确引用 `design.md` 的相关章节（用 § 编号）。

6.  **依赖关系与并行性原则**:
    - **依赖关系**: 若任务间存在强依赖，需在描述中简要说明（如 "依赖任务 X 完成"）。
    - **并行标记**:
      - 默认：对可并行执行的任务追加 ` (P)`。
      - `--sequential` 模式：省略所有 ` (P)` 标记。

7.  **粒度控制原则**:
    - **最大工时**: 单任务预计工时不超过 8 小时。如果超过 8 小时，必须进一步拆解。

#### 2.2 生成任务清单

1.  **按模板生成任务列表**:
    - 严格使用 `.cursor/commands/spec-templates/task.md` 的复选框结构输出任务清单。
    - 选择"仅主任务"或"主任务 + 子任务结构"中更合适的格式。
    - 按功能模块分组，使用 `##` 标题分隔。
    - **任务标题格式**: 任务标题本身不包含模块名前缀，模块名通过其所属的 `##` 二级标题自动识别。同步到禅道时，将标题格式化为 `【模块名】任务名称` 作为 `post_tasks` 的 `name`。

2.  **生成依赖关系图**:
    - 在任务列表后添加 `## 依赖关系` 章节。
    - 使用 Mermaid `graph TB` 格式绘制任务依赖图。
    - **体现 V 模型逻辑**: 确保图表体现 `[契约定义] --> [开发] --> [联调]` 的流向。
      ```mermaid
      graph TB
          Contract[契约/模型定义] --> DevBack[后端开发]
          Contract --> DevFront[前端开发]
          DevBack --> Integration[集成联调]
          DevFront --> Integration
      ```

3.  **生成任务统计**:
    - 在依赖图后添加 `## 任务统计` 章节，包含:
      - 总任务数
      - 已完成数 / 待执行数
      - 按模块分类的任务数
      - 预计总工时（人天换算：8小时 = 1人天）
      - 可并行任务数

4.  **生成任务执行建议**:
    - 在统计后添加 `## 任务执行建议` 章节，按阶段划分:
      ```
      ### 第一阶段：基础能力(X-Y天)
      1. 任务A (ID: xxx) - 说明
      2. 任务B (ID: xxx) - 可并行
      
      ### 第二阶段：核心功能(X-Y天)
      ...
      ```

5.  **生成风险提示**:
    - 在执行建议后添加 `## 风险提示` 章节:
      ```
      ⚠️ **关键依赖**：
      - 外部服务依赖说明
      
      ⚠️ **技术风险**：
      - 重点验证项
      
      ⚠️ **需要补充信息**：
      - [ ] 待确认事项
      ```

6.  **禅道回填占位**:
    - 每条待同步任务在 `需求：` 行之后预留：`禅道任务ID：<待回填>`。

7.  **保存文档**:
    - 保存为: `onespec/changes/<id>-<name>/tasks.md`。

> ⚠️ **强制衔接**: `tasks.md` 保存完成后，**无需用户确认，立即自动执行步骤3**（同步至禅道）。不得在此处暂停或向用户呈现中间结果。

### 3. 同步至禅道 (MCP) ⚠️ 必选步骤，自动执行
1.  **获取现有任务 (去重)**:
    - 调用 **`get_executions_executionID_tasks`**：`executionID` = 当前执行/迭代 ID（须从用户输入或上下文获取）。
    - 用返回列表中每条任务的 `name`（标题）建立 **`【模块名】任务名称` → taskID** 映射。
2.  **创建/跳过**:
    - 遍历 `tasks.md` 任务；**格式化标题** 同前（`【模块名】任务名称`）。
    - **若标题已存在于映射**：跳过创建，将已有 `taskID` 写入 `禅道任务ID：`。
    - **若不存在**：调用 **`post_tasks`**：
      - `name` = 格式化标题
      - `executionID` = 当前执行/迭代 ID
      - `type` = `devel`
      - `assignedTo` = **仅当**用户提供 **`--assign`** 时写入；否则 **不传该字段**（见上文「MCP / Token 与负责人」）
      - `story` = 禅道 Story 数字 **id**（与 `proposal` frontmatter / 简写 **storyId** 一致时填写，便于执行下关联需求）
    - 成功则把返回的任务 id 写入 `禅道任务ID：`。

### 4. 结果汇总
- 更新 `tasks.md`，每条任务尽量带 `禅道任务ID`。
- 输出简报：共 N 个任务，新建 X，跳过 Y，失败 Z。

## 关键约束
- **模板遵循**: `tasks.md` 遵循 `spec-templates/task.md`，并增加 `禅道任务ID：` 行用于回填。
- **不编造**: 无法从 `design.md` 推导的需求 ID、工时、迭代等信息不得臆造；缺失则留空并在输出中提示。
- **路径基准**: 命令中的文件读写路径以本命令文件所在仓库的根目录为基准，不限制跨工作区的上下文收集。
</instructions>

## 输出描述

生成的 `tasks.md` 必须包含以下章节:

### 必需章节
1. **任务说明** (开头): 说明任务类型图例（✅ 已存在任务、🆕 新创建任务、`(P)` 并行标记）
2. **任务列表**: 按功能模块分组的任务清单（使用 `##` 标题分隔模块）
3. **依赖关系**: Mermaid 图表展示任务依赖
4. **任务统计**: 总任务数、已完成/待执行、预计工时、可并行任务数
5. **任务执行建议**: 按阶段划分的执行顺序建议
6. **风险提示**: 关键依赖、技术风险、需补充信息

### 执行完成后输出
1. **状态**: 确认 `tasks.md` 已在 `onespec/changes/<id>-<name>/tasks.md` 生成/更新
2. **同步结果**: 新增/跳过/失败数量与原因摘要
3. **风险提示**: 需要人工补齐的信息（如简写多目录、`executionID` 不明、同步失败需核对 token 权限等）

## 安全与回退
### 错误场景
**设计文档缺失（完整模式）**:
- `design.md` 不存在且**未使用 `--no-design`**：停止执行
- **用户消息**: "未找到详细设计文档。如需跳过设计阶段，请使用 `--no-design` 参数；或先运行 `onespec-design` 生成 design.md。"
