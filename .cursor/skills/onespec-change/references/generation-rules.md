# 智能填充规范

## 1. Proposal 填充规范

### 1.1 基础信息（严格替换）

⛔ **来源隔离原则（必须遵守）**：
下表所有字段的值必须且只能来自**当次禅道 `get_stories_storyID`（或兼容场景下其它已配置 MCP）的返回结果**。
禁止从以下来源读取这些字段：
- 对话历史中的任何已生成内容（PRD、原型、设计文档）
- 原型 Mock 数据中的虚构人名
- 用户在对话中提及的任何人名

| 占位符 | 替换内容 |
|--------|---------|
| `<工作项ID>` | 禅道 Story ID（或兼容系统需求 ID） |
| `<user>` | 当前操作系统用户名 |
| `[需求标题]` | API 返回结果中标题字段的**原始值** |
| `[处理人]` | API 返回结果中 `处理人` 字段的**原始值** |
| `<priority>` | API 返回结果中 `优先级` 字段的**原始值** |
| `[API返回的需求描述]` | 工作项返回的完整描述（原文，禁止意译或删减） |

### 1.2 智能生成章节

**变更详情 (Change Analysis)**：
- `From`：描述当前代码逻辑现状（若为全新功能则填「无」）
- `To`：用 EARS 语法描述目标行为（必填，见 §1.3 示例）
- `Impact`：无 / 破坏性变更 / 数据迁移（三选一）

**规范变更规划 (Spec Impact)**：根据受影响的代码模块，推断需要新增或修改的 Spec 列表。
格式：`- [ ] **Added**: \`specs/模块/文件.md\` - 一句话说明该 Spec 的范围`

**验证计划 (Test Plan)**：根据变更逻辑，生成核心测试场景，每条一行，可直接作为测试用例起点。

### 1.3 EARS 语法示例（Few-shot）

```
主流程：  When 用户提交订单，the 订单服务 shall 创建订单记录并返回 orderId。
前置约束：If 用户未登录，the 认证服务 shall 拒绝请求并返回 HTTP 401。
持续状态：While 库存为 0，the 商品服务 shall 禁止将商品加入购物车并展示缺货提示。
```

主语选择规则：使用软件系统/服务名称（如「订单服务」「认证网关」），不使用「系统」「后端」等模糊主语。

## 2. Delta Spec 精化规范

### 2.1 精化原则

| 章节 | 精化要求 |
|------|---------|
| 文档标题 | 使用 Spec Impact 条目的描述；在引言中注明对应 `proposal.md §2.x` 编号，建立引用关系 |
| 需求描述 (EARS) | 以 proposal.md 粗粒度 EARS 为基础，**补充**主流程、前置约束、异常与边界——不得简单复制 |
| 验收标准 | 以 proposal.md 测试场景为起点，**细化**为含「给定前提 / 执行操作 / 预期结果」的可测试标准 |
| 范围说明 | 明确本 Spec 与相邻 Spec 的分工，防止跨文件重叠 |

### 2.2 精化 vs 复制判断

- ✅ **精化**：proposal.md 描述「创建订单」→ Delta Spec 补充「幂等键规则、超时重试、并发锁策略、订单号生成格式」
- ❌ **复制**：将 proposal.md 的 EARS 句子原封不动粘贴，无任何新增约束

### 2.3 Frontmatter 填写

- `specType: added`：新增规范文件（不依赖已有 Spec）
- `specType: modified` + `targetSpec: <原文件路径>`：修改已有规范文件
- 无法精化的章节：保留模板占位符，由用户补充，不编造内容
