# 任务拆解规则

## 1. 拆解原则

| 原则 | 规则 |
|------|------|
| **契约先行** | 涉及前后端或跨模块调用时，编码任务前**必须**拆解"接口定义/契约确认"任务；复杂业务流程（≥2个模块）**必须**拆解独立"集成联调"任务。契约产物须包含：接口/方法签名、字段协议、映射规则、fail-safe 策略之一 |
| **模块化组织** | 按功能模块用 `##` 分组，分组顺序见下表；优先识别并提取基础/公共能力 |
| **按功能拆分** | 按功能特性拆分（而非前后端分离），确保每个任务是可独立验收的最小价值单元 |
| **信息完整性** | 每个任务必须包含：预计工时、详细变更说明（文件路径 + 修改逻辑，按接口/配置/后端/前端/SQL 分类）、设计章节引用（`参考：design.md § X.X`）、测试覆盖率要求（核心功能 ≥80%，一般功能 ≥70%） |
| **可追溯性** | 需求追溯 ID 紧随任务标题第一行（`需求：{{REQUIREMENT_IDS}}`）；同步后追加 `禅道任务ID：{{TASK_ID}}` |
| **依赖与并行** | 强依赖须在描述中说明；可并行任务追加 ` (P)` 标记（`--sequential` 模式除外） |
| **粒度控制** | 单任务预计工时建议在 **2h~4h** 区间；超过 8h **必须**拆分；低于 2h 应合并到功能上最相关的任务 |

> **契约例外**：若所谓"契约"仅为新增一个常量（无新接口、无新方法签名），则并入相关实现任务，无需独立契约任务。

### 模块分组顺序

| 顺序 | 模块分组 | 典型内容 |
|------|---------|---------|
| 1 | 契约/模型定义 | 接口签名、字段协议、数据结构 |
| 2 | 核心业务功能 | 主要功能实现 |
| 3 | 配置管理 | 参数、Feature Flag、配置项 |
| 4 | 性能优化与安全 | 非功能性需求 |
| 5 | 集成联调与验收 | 端到端测试、联调任务 |
| 6 | 文档与发布 | 文档、上线操作 |

## 2. tasks.md 必需章节（共 6 个）

1. **任务说明**（开头）：图例说明（✅ 已存在任务、🆕 新创建任务、`(P)` 并行标记）
2. **任务列表**：按功能模块 `##` 分组的任务清单
3. **依赖关系**：Mermaid `graph TB` 图，体现 `[契约] → [开发] → [联调]` V 模型流向
4. **任务统计**：总任务数、已完成/待执行、按模块分类数、预计总工时（8h=1人天）、可并行任务数
5. **任务执行建议**：按阶段划分（第一阶段：基础能力 X-Y 天；第二阶段：核心功能...）
6. **风险提示**：关键依赖、技术风险、需补充信息（⚠️ 格式）

## 3. 正例（粒度参考）

```markdown
- [ ] 1. 用户权限校验接口定义 (P)
  - 需求：REQ-001
  - 参考：design.md § 2.1
  - 预计工时：3h
  - **接口/契约**：
    - `api/user/permission.ts`：新增 `checkPermission(userId, resource)` 方法签名，返回 `PermissionResult`
  - **后端代码变更**：
    - `services/PermissionService.java`：实现接口，调用 RBAC 规则引擎
  - 测试覆盖率：≥80%（核心功能）
```

> **粒度判断**：此任务 3h，含接口定义 + 实现，属于合理范围。若校验逻辑复杂（>8h），应拆分为「接口定义（1h）」+「规则引擎实现（4h）」+「异常处理（2h）」。

---

## 4. 禁止事项

- 禁止臆造无法从 `design.md` 推导的需求 ID、工时、迭代信息；缺失则留空并提示
- 禁止单任务超过 8h 不拆分
- 禁止将「接口定义」与「复杂实现」合并为 1 个任务（当工时超过 4h 时）
- 禁止以前后端分离（而非功能特性）作为拆分维度
