# 需求分析规则

本文件定义需求分析的核心逻辑，在生成 PRD 前执行。

## 输入

- `user-story`: 原始需求描述
- `feature-name`: 功能标识符
- `project-context`: 现有代码与文档上下文

## 输出

- 澄清问题清单（发现模糊点时）
- 分析通过确认（需求清晰时）

---

## 分析步骤

### 1. 上下文探索

建立需求与现有系统的映射关系。**核心原则：结构导航 → 符号定位 → 切片读取。禁止盲目全量扫描。**

1. **结构认知**：
   - 先确认模块目录结构（如 `ls -R src/modules`），避免在错误的目录中搜索。
   - 优先关注 `types/`, `interfaces/`, `api/` 等高密度信息目录。

2. **定位策略**：
   - **L1 精确查找（优先）**：已知或能推测出类名/文件名时（如 `UserBO`），必须使用 `Glob` 或 `Grep`。
   - **L2 语义搜索（兜底）**：仅在无法推测名称时使用 `SemanticSearch`。
     - *示例*："订单取消的校验逻辑"（业务行为）
     - *禁止*：用 SemanticSearch 搜 "UserController"（这是精确名称，应用 Glob）。

3. **读取约束**：
   - **接口优于实现**：优先读取 Interface 定义或方法签名，确认输入输出。
   - **切片读取**：命中文件后，使用 `Read(offset, limit ≤ 60)`。
   - **禁止全量**：严禁对 >100 行的文件进行无参数 `Read`。

4. **大文件处理**：
   - **步骤**：`Grep (获取行号)` → `Read (offset=行号, limit=30)`。
   - **例外**：仅在重构涉及全类上下文时，允许分块读取，但需在 Plan 中显式声明。

5. **降级熔断**：
   - 搜索路径：`Glob/Grep` → `SemanticSearch` (最多2次) → `Ask User`。
   - 避免 Agent 在无结果时反复尝试不同关键词，浪费 Token。

### 2. 逻辑漏洞检测

找出需求中的模糊、冲突或缺失点。

检查维度：

| 维度 | 关键问题 |
|------|----------|
| **角色与权限** | 谁可以执行？需要特殊权限吗？ |
| **数据流转** | 输入来源？存储位置？输出给谁？ |
| **异常流程** | 网络失败、校验不通过、关联数据不存在时如何处理？ |
| **状态机** | 业务对象的状态流转是否闭环？ |

### 3. 输出判定

根据分析结果选择路径：

#### 路径 A: 发现模糊点

触发条件：
- 缺少关键字段定义
- 业务流程中断
- 与现有代码逻辑冲突且未说明原因

**执行动作**：生成 `<feature-name>-questions.md`

```markdown
# 需求澄清问题 - <feature-name>

> 基于 User Story: "..."

## 问题 1: [问题标题]

[问题描述]

- **上下文**: 发现现有代码中存在...
- **风险**: 如果不明确，可能导致...

### 回答

[等待用户填写]
```

#### 路径 B: 需求清晰

触发条件：需求逻辑自洽，与现有系统兼容

**执行动作**：输出分析摘要

```markdown
## 需求分析通过

- **核心功能**: [功能列表]
- **涉及模块**: [文件路径]
- **关键约束**: [约束描述]
```
