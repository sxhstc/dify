# 前端代码评审规则

## 🎯 核心功能

**本规则用于评审前端待提交代码，确保代码质量：**
1. 自动获取 Git 暂存区的代码变更
2. 进行全面的代码评审（潜在 Bug、性能问题、代码规范）
3. 输出详细的优化建议
4. 与开发者确认后执行优化
5. 优化后重新评审，确保问题已解决

**使用方式：**
- 开发者在 Cursor 对话中引用此规则（`@rules frontend-code-review`）
- 规则自动获取暂存区变更并进行评审
- 输出优化建议，等待开发者确认
- 确认后执行优化，并重新评审

## 📋 第一步：获取 Git 暂存区变更

### 1.1 检查 Git 状态

**执行以下命令获取变更信息：**

```bash
# 检查是否有暂存区的变更
git status --short

# 获取暂存区的文件列表（已 git add）
git diff --cached --name-status

# 获取暂存区的详细变更内容
git diff --cached

# 获取暂存区的变更统计
git diff --cached --stat
```

### 1.2 过滤不需要评审的文件

**在评审前，需要排除以下类型的文件：**

**排除的文件类型：**
- **配置文件**（项目配置文件，无需评审）：
  - `package.json` (npm 项目配置)
- **Lock 文件**（依赖锁定文件，自动生成，无需评审）：
  - `package-lock.json` (npm)
  - `yarn.lock` (yarn)
  - `pnpm-lock.yaml` (pnpm)
  - `poetry.lock` (Python poetry)
  - `Pipfile.lock` (Python pipenv)
  - `Gemfile.lock` (Ruby)
  - `composer.lock` (PHP)
- **其他自动生成文件**：
  - 构建产物（`dist/`, `build/`, `.next/` 等）
  - 日志文件（`*.log`）
  - 临时文件（`.tmp`, `.temp` 等）

**过滤逻辑：**
```bash
# 获取暂存区文件列表后，过滤掉配置文件和 lock 文件
git diff --cached --name-only | grep -v -E '(package\.json|package-lock\.json|yarn\.lock|pnpm-lock\.yaml|poetry\.lock|Pipfile\.lock|Gemfile\.lock|composer\.lock)'
```

**如果检测到配置文件和 lock 文件：**
```
ℹ️ 检测到以下文件已自动排除（无需评审）：

- package.json (npm 项目配置文件)
- package-lock.json (npm 依赖锁定文件)
- yarn.lock (yarn 依赖锁定文件)
- pnpm-lock.yaml (pnpm 依赖锁定文件)

这些文件为项目配置文件或由包管理器自动生成，无需进行代码评审。
```

### 1.3 变更文件分类

**根据文件类型进行分类：**

| 文件类型 | 扩展名 | 评审重点 |
|---------|--------|---------|
| **组件文件** | `.vue`, `.tsx`, `.jsx` | 组件逻辑、Props 验证、生命周期、性能优化 |
| **工具函数** | `.ts`, `.js` | 函数逻辑、边界条件、错误处理、性能 |
| **样式文件** | `.css`, `.scss`, `.less` | 样式规范、性能影响、兼容性 |
| **配置文件** | `.json`, `.config.*` | 配置正确性、格式规范（排除 lock 文件） |
| **测试文件** | `.test.*`, `.spec.*` | 测试覆盖率、测试质量 |
| **类型定义** | `.d.ts` | 类型定义完整性、准确性 |

### 1.4 处理未暂存文件

**如果存在未暂存的文件：**

```
⚠️ 检测到未暂存的文件：

- src/components/NewComponent.vue (未暂存)
- src/utils/helper.ts (未暂存)

请选择：
1. 只评审已暂存的文件（git add 的文件）
2. 暂存所有变更后评审（git add .）
3. 取消评审
```

**根据开发者选择执行相应操作。**

### 1.5 无变更处理

**如果暂存区没有变更（或所有变更都是配置文件和 lock 文件）：**

```
⚠️ 暂存区没有需要评审的代码变更

可能情况：
1. 暂存区为空（未执行 git add）
2. 暂存区只有配置文件和 lock 文件（已自动排除）
3. 所有变更文件都在排除列表中

请确认：
1. 是否已经执行 git add？
2. 是否需要评审工作区的变更？
3. 或者取消本次评审？
```

## 🔍 第二步：代码评审

### 2.1 评审维度

**代码评审必须覆盖以下四个维度：**

#### 维度 1：潜在 Bug 检测

**重点关注：**

1. **空值和未定义处理：**
   - ✅ 检查是否对 `null`、`undefined` 进行了适当处理
   - ✅ 检查可选链操作符（`?.`）的使用
   - ✅ 检查空值合并操作符（`??`）的使用
   - ❌ 发现：直接访问可能为空的属性

2. **数组和对象操作：**
   - ✅ 检查数组边界（索引越界）
   - ✅ 检查对象属性是否存在
   - ✅ 检查 `map`、`filter`、`reduce` 等方法的空数组处理
   - ❌ 发现：未检查数组长度就访问元素

3. **异步操作：**
   - ✅ 检查 `async/await` 的错误处理（`try-catch`）
   - ✅ 检查 Promise 的 `catch` 处理
   - ✅ 检查竞态条件（race condition）
   - ❌ 发现：未处理异步操作的错误

4. **类型安全：**
   - ✅ 检查 TypeScript 类型断言的安全性
   - ✅ 检查类型守卫的使用
   - ✅ 检查 `any` 类型的使用（应避免）
   - ❌ 发现：不安全的类型转换

5. **边界条件：**
   - ✅ 检查极值处理（0、负数、极大值）
   - ✅ 检查空字符串、空数组、空对象
   - ✅ 检查特殊字符和编码问题
   - ❌ 发现：缺少边界条件检查

6. **副作用和状态管理：**
   - ✅ 检查状态更新的正确性
   - ✅ 检查依赖数组的完整性（React hooks、Vue watch）
   - ✅ 检查内存泄漏（事件监听器未清理）
   - ❌ 发现：状态更新可能导致无限循环

#### 维度 2：性能问题检测

**重点关注：**

1. **渲染性能：**
   - ✅ 检查不必要的重新渲染
   - ✅ 检查 `useMemo`、`useCallback`（React）的使用
   - ✅ 检查 `computed`、`watch`（Vue）的优化
   - ❌ 发现：组件在每次渲染时都创建新对象/函数

2. **列表渲染：**
   - ✅ 检查虚拟滚动（长列表）
   - ✅ 检查 `key` 属性的正确使用
   - ✅ 检查列表项组件的优化
   - ❌ 发现：长列表未使用虚拟滚动

3. **资源加载：**
   - ✅ 检查图片懒加载
   - ✅ 检查代码分割（code splitting）
   - ✅ 检查资源预加载/预取
   - ❌ 发现：大图片未使用懒加载

4. **计算复杂度：**
   - ✅ 检查循环嵌套（O(n²) 或更高）
   - ✅ 检查递归深度
   - ✅ 检查大数据处理
   - ❌ 发现：嵌套循环导致性能问题

5. **网络请求：**
   - ✅ 检查请求去重（防抖/节流）
   - ✅ 检查请求缓存
   - ✅ 检查并发请求数量
   - ❌ 发现：频繁发起相同请求

6. **内存使用：**
   - ✅ 检查大对象/数组的创建
   - ✅ 检查闭包导致的内存泄漏
   - ✅ 检查事件监听器的清理
   - ❌ 发现：未清理的事件监听器

#### 维度 3：代码规范检测

**重点关注：**

1. **命名规范：**
   - ✅ 检查变量、函数、组件命名是否符合规范
   - ✅ 检查命名是否清晰、有意义
   - ✅ 检查是否使用缩写（应避免）
   - ❌ 发现：命名不符合项目规范

2. **代码结构：**
   - ✅ 检查函数/组件长度（建议 < 100 行）
   - ✅ 检查嵌套深度（建议 < 4 层）
   - ✅ 检查代码重复（DRY 原则）
   - ❌ 发现：函数过长，需要拆分

3. **注释和文档：**
   - ✅ 检查复杂逻辑是否有注释
   - ✅ 检查函数/组件是否有 JSDoc 注释
   - ✅ 检查注释是否准确、有用
   - ❌ 发现：复杂逻辑缺少注释

4. **导入和导出：**
   - ✅ 检查导入顺序（第三方库、项目模块、相对路径）
   - ✅ 检查未使用的导入
   - ✅ 检查循环依赖
   - ❌ 发现：存在未使用的导入

5. **代码格式：**
   - ✅ 检查缩进、空格、换行
   - ✅ 检查引号使用（单引号/双引号）
   - ✅ 检查分号使用
   - ❌ 发现：代码格式不符合项目规范

6. **最佳实践：**
   - ✅ 检查是否遵循框架最佳实践（React/Vue）
   - ✅ 检查是否使用推荐的 API
   - ✅ 检查是否避免反模式
   - ❌ 发现：使用了不推荐的做法

#### 维度 4：单元测试检查

**重点关注：**

1. **测试文件存在性：**
   - ✅ 检查新增/修改的代码是否有对应的测试文件
   - ✅ 检查测试文件位置是否符合项目规范（通常与被测试文件在同一目录）
   - ✅ 检查测试文件命名是否符合规范（`.test.*` 或 `.spec.*`）
   - ❌ 发现：新增组件/函数缺少对应的测试文件

2. **测试覆盖率：**
   - ✅ 检查新增/修改代码的测试覆盖率
   - ✅ 检查是否满足项目覆盖率要求（参考 UTDD 规范）
   - ✅ 检查关键逻辑是否被测试覆盖
   - ❌ 发现：测试覆盖率不足，未达到项目要求

3. **测试用例完整性：**
   - ✅ 检查是否覆盖正常使用场景（Happy Path）
   - ✅ 检查是否覆盖边界条件（空值、极值、特殊字符）
   - ✅ 检查是否覆盖错误处理（无效输入、异常情况）
   - ✅ 检查组件测试是否覆盖渲染、Props、交互、条件渲染
   - ❌ 发现：测试用例不完整，缺少关键场景

4. **测试代码质量：**
   - ✅ 检查测试代码是否清晰、可读
   - ✅ 检查测试是否独立（不依赖其他测试）
   - ✅ 检查是否使用了适当的 Mock 和 Stub
   - ✅ 检查测试描述是否清晰（describe/it 的描述）
   - ❌ 发现：测试代码质量不佳，难以维护

5. **测试框架和工具：**
   - ✅ 检查是否使用了正确的测试框架（Vitest/Jest/Mocha）
   - ✅ 检查是否使用了正确的测试工具库（@vue/test-utils/@testing-library/react）
   - ✅ 检查测试环境配置是否正确（DOM 环境、路径别名等）
   - ❌ 发现：测试框架或工具使用不当

6. **测试执行状态：**
   - ✅ 检查测试是否能够正常执行
   - ✅ 检查测试是否全部通过
   - ✅ 检查是否有失败的测试或跳过的测试
   - ❌ 发现：存在失败的测试或测试无法执行

**测试覆盖率要求（参考 UTDD 规范）：**

| 代码类型 | 语句覆盖率 | 分支覆盖率 | 函数覆盖率 | 行覆盖率 |
|---------|-----------|-----------|-----------|---------|
| **核心业务逻辑** | ≥ 85% | ≥ 80% | ≥ 85% | ≥ 85% |
| **工具函数/工具类** | ≥ 80% | ≥ 75% | ≥ 80% | ≥ 80% |
| **UI 组件（交互型）** | ≥ 80% | ≥ 75% | ≥ 80% | ≥ 80% |
| **UI 组件（展示型）** | ≥ 70% | ≥ 65% | ≥ 70% | ≥ 70% |

**特殊情况处理：**
- **配置文件**：`package.json`, `tsconfig.json`, `vite.config.ts` 等可跳过代码评审和测试
- **纯样式文件**：`.css`, `.scss`, `.less` 可跳过测试（建议视觉回归测试）
- **类型定义文件**：`.d.ts` 通过 TypeScript 编译检查，可跳过测试
- **遗留代码修改**：修改的遗留代码应至少提升 5% 覆盖率，或达到 `max(原覆盖率, 目标阈值 - 10%, 60%)`
- **部分修改场景**：修改的行必须达到 ≥ 80% 覆盖率

```

## 📌 总结

**本规则的核心功能：**

1. **自动获取变更** - 从 Git 暂存区获取待提交代码
2. **全面代码评审** - 覆盖潜在 Bug、性能问题、代码规范
3. **详细优化建议** - 提供具体的问题描述和修复方案
4. **交互式优化** - 与开发者确认后执行优化
5. **重新评审验证** - 优化后重新评审，确保问题已解决

**规则章节概览：**
- **第一步**：获取 Git 暂存区变更（状态检查、文件过滤、文件分类、未暂存处理）
- **第二步**：代码评审（Bug 检测、性能检测、规范检测、单元测试检测）
- **第三步**：生成优化建议（建议汇总、优化方案、批量优化）
- **第四步**：确认并执行优化（展示建议、交互确认、执行优化）
- **第五步**：重新评审（优化后评审、验证修复、最终确认）
- **第六步**：异常情况处理（Git 仓库、变更获取、工具可用性、优化失败、测试环境）
- **第七步**：使用示例（基本流程、选择性优化、自定义选择）

**评审重点：**
- 🔴 **潜在 Bug** - 空值处理、类型安全、异步错误、边界条件
- 🟡 **性能问题** - 渲染优化、列表性能、资源加载、计算复杂度
- 🟢 **代码规范** - 命名规范、代码结构、注释文档、最佳实践
- 🧪 **单元测试** - 测试存在性、覆盖率、测试用例完整性、测试代码质量

**使用场景：**
- ✅ 提交代码前的质量检查
- ✅ 代码优化和重构
- ✅ 团队代码评审
- ✅ 持续集成前的本地检查
